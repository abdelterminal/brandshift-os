# Migrating from the old app

`abdelterminal/brandshiftsaas` — Angular + Django + MongoEngine over a Mongo called `mediast_db` —
is the app this one replaces. This is how its data gets here, what arrives, and what does not.

Read it before running anything. The migration itself is safe to run repeatedly; the decisions it
makes on your behalf are the part worth understanding first.

---

## What it does

```bash
# Look, and write nothing. This is the default.
npm run db:migrate:mongo -- --uri mongodb://localhost:27017

# Do it.
npm run db:migrate:mongo -- --uri mongodb://localhost:27017 --commit
```

| Flag | Default | What it is |
|---|---|---|
| `--uri` | *required* | Where the old Mongo is. |
| `--db` | `mediast_db` | Database name inside it. |
| `--org` | `brandshift` | Slug of the organization everything lands in. |
| `--org-name` | `BrandShift` | Its display name. |
| `--currency` | `MAD` | ISO 4217. One currency per organization — see `KNOWN-GAPS.md`. |
| `--timezone` | `Africa/Casablanca` | Every date on every screen is read in this. |
| `--commit` | off | Without it, nothing is written. |

Three properties are worth knowing before you run it:

- **It reads only.** Nothing is written back to Mongo, and the connection prefers a secondary.
  The old app stays the system of record until you decide otherwise.
- **It is one transaction.** Either the whole migration lands or the database is exactly as it
  was. There is no half-migrated state to clean up.
- **It can be run again.** Every row lands on an id derived from its Mongo `_id`, so a second run
  updates what the first one wrote rather than duplicating it. Rehearse, read the report, fix,
  repeat.

## What arrives

| Old | New | Notes |
|---|---|---|
| `user` | `users` + `memberships` | Identity and org membership are separate here. |
| `department` | `departments` | Name, and the two descriptive fields joined into one. |
| `project.client` | `companies` | The free-text client name becomes a real CRM company. |
| `project` | `projects` | Plus a generated key — see below. |
| `project.tasks[]` | `tasks` | Embedded documents become rows, order preserved. |
| `project.employees[]` | `project_members` | The resolved owner becomes the lead. |
| `activity_events` | `activity_events` | Verbs translated; unknown ones skipped and counted. |

### Decisions it makes, and why

**Everyone keeps their password.** The old app stored Django's `pbkdf2_sha256`; this one writes
scrypt. Rather than reset seven passwords by email — there is no mail transport — `verifyPassword`
reads the old format, and the first successful sign-in re-hashes to scrypt. A migrated hash
survives exactly one login and is never written back. The read path is tested against a vector
generated by the old app's own Django, not from memory.

**The earliest `ADMIN` becomes the owner.** An organization needs exactly one founder and the old
schema has no such flag. Remaining `ADMIN`s become `admin`; every `EMPLOYEE` becomes `member`.
**Nobody is promoted to `manager`** — the old data records nothing that would justify it, and
handing out a permission nobody granted is the worst thing a migration can do quietly. The owner
keeps all four module flags, because the old `ADMIN` could already see everything.

If there is no `ADMIN` at all, the run refuses rather than choosing an owner for you.

**Clients typed twice become one company.** The real data holds `"Obarfum "` and `"Ô Bar’Fum"` on
different projects: one client, two people, two days. They are grouped by a fold of the name —
case, accents, and everything that is not a letter or digit removed — which is enough to see those
two are the same and is *not* fuzzy matching: no edit distance, no threshold, nothing that could
pull two genuinely different clients together. The spelling kept is the longest one, because that
is where the detail is. **Every merge is printed by name in the report**, so you can see each one.

**Project keys are generated.** Projects here are reached by a two-to-five letter key and the old
app has none. They come from the initials of the name — `Mr Dyaf - Filmmaking` becomes `MDF`. The
key format forbids digits, so collisions are settled by taking more letters out of the name, and
only then by walking a suffix letter.

**Project owners are resolved only when unambiguous.** The old `owner` is a first name somebody
typed. It is matched to a person only when exactly one person answers to it; two Youssefs and the
field is left empty, with a count in the report. Guessing which one owns the work is not a thing a
migration gets to do.

**A cancelled project becomes an archived one.** This app has no cancelled project. The two are
not the same sentence, so the count is reported rather than passed over.

**A task in review becomes in progress.** Not `done`: work in review is work somebody may still
hand back, and calling it finished would take it off the screen of the person who has to look at
it. An archived task becomes `cancelled` whatever it said before.

## What does not arrive

Each of these is counted and printed by the report every run. None of them is an oversight.

| Not carried | Why |
|---|---|
| Sign-in sessions | The token format, the secret and the digest are all different. Everybody signs in once, with the password they already had. |
| Attendance and lunch records | There is no timeclock here — attendance means who is away, derived from approved leave. Already in `KNOWN-GAPS.md`. |
| Direct messages | This app has channels, not one-to-one messages. Turning each pair of people into a private channel would invent a structure nobody asked for. |
| Meetings | The old meeting has a start and no end, no responses and no location. Carrying them needs a default duration somebody has to choose. |
| Department icons and images | Base64 in a text column is not file storage, and this app has none yet. |
| Project budgets | A free-text string with no currency. Money here is integer cents on a quote or an invoice; turning a note into a financial document would be inventing one. |
| Project durations | Free text such as `4 days`. The start date and deadline carry the real thing. |
| Project tags | A mix of client names and department names, both of which are now real columns pointing at real rows. |
| Task progress percentages | A task here is todo, in progress, blocked, done or cancelled. A number nobody updates is worse than no number. |
| Task refusal workflow | `refusal_pending` and `refused_by` have no equivalent. The `rejection_reason` text is kept, on the task. |
| Activity events with an unknown verb | Storing them under an invented verb would put rows in the feed that nothing knows how to render. |

Free text that would otherwise be lost is kept rather than dropped: a task's `note` and
`rejection_reason` are appended to its description under a label.

## Running it for real

1. **Back the old database up first.** `backup-data.ps1` in the old repo runs `mongodump`. Do this
   even though the migration only reads.
2. **Rehearse on a copy.** Point `--uri` at a Mongo restored from that dump, and `DATABASE_URL` at
   a scratch Postgres. Nothing about the rehearsal has to be undone — throw the scratch database
   away.
3. **Read the report.** Specifically the merges under *Decisions this run made* and anything under
   *Worth a look before committing*.
4. **Apply the schema**, then run with `--commit`:
   ```bash
   npm run db:migrate            # drizzle-kit migrate, on the target database
   npm run db:migrate:mongo -- --uri <uri> --commit
   ```
5. **Tell people to sign in with the password they already had.** Nothing was reset.

### Rehearsing without touching the old data at all

The old deployment keeps its Mongo in a Docker volume. Copying it is cheaper than a dump and
restore, and leaves the original untouched:

```bash
docker volume create rehearsal
docker run --rm -v brandshift_saas_mongodb_data:/from:ro -v rehearsal:/to alpine \
  sh -c "cp -a /from/. /to/"
docker run -d --name mongo-rehearsal -p 27018:27017 -v rehearsal:/data/db mongo:7.0 --noauth
```

Then point `--uri` at `mongodb://localhost:27018`. Delete the container and the volume afterwards.

# The Notion SOP import -- a separate source

`db:migrate:mongo` moves the old *app's* data. It does not move the old *Notion workspace*,
which is where Mediast Creative actually wrote down how the work is done. A full Notion API
export of that workspace (`Mediast_OS_API_Raw_Export.json`) was provided later, and one script
brings the useful part of it across:

```bash
# Look, and write nothing. This is the default.
npm run db:import:sops -- --file ./Mediast_OS_API_Raw_Export.json

# Do it.
npm run db:import:sops -- --file ./Mediast_OS_API_Raw_Export.json --commit
```

| Flag | Default | What it is |
|---|---|---|
| `--file` | *required* | Path to the raw Notion export JSON. |
| `--org` | `mediast` | Slug of the organization the procedures land in. |
| `--commit` | off | Without it, nothing is written. |

## Why only the SOPs

The export has 28 Notion "databases", but 20 are filtered views. Of the eight real ones, only
the **SOP Library — Mediast Creative** holds substantial written content: twelve procedures,
each with the same twelve sections (🎯 Objective … ➡️ Next Step). Projects (22), Tasks (39) and
Team (7) are name-only, and every one of them overlaps a row `db:migrate:mongo` already carries
*with* dates, owners and status -- importing the Notion copies would duplicate. Clients, CRM,
Objectives & KPI and Weekly Reviews are empty. So this importer touches `sops` and `sop_steps`
and nothing else.

## What it does

- Each Notion page becomes one `sops` row: title, `summary` from the 🎯 Objective section,
  `status = "draft"` (the Notion rows are all drafts, "à valider avec l'équipe"),
  `created_by_user_id` = the target org's owner. Each of the twelve sections becomes one
  `sop_steps` row -- heading as the step title, the section's blocks flattened to plain text
  (`- ` bullets, `[ ] ` checklist items, `### ` sub-steps) as the detail.
- **Owner and department are left null** -- see `KNOWN-GAPS.md`. The Notion "Owner" is a role
  title, not a department here, and the SOP-owner relation points at Team pages that are not
  people in this org.
- **Re-runnable.** Row ids are derived from the Notion page id (`identity.ts`, a UUIDv5 with
  its own namespace, distinct from the Mongo migration's), so a second run updates the same
  rows. A procedure's steps are replaced wholesale each run.
- The dry run prints new-vs-updated counts, the org and author it resolved, and any title that
  needed its slug suffixed. Nothing is written without `--commit`.
